# Вторая неделя

*Фиксировать, просматривать, разрешать, предлагать — не уходя в другой инструмент.*

Первый час — это открыть проект и запустить его. Вторая неделя — всё,
что вокруг кода: двадцать коммитов в день, диф, который надо прочитать
перед каждым, конфликт после pull, pull request после push, трассировка
стека, по которой надо пройти, README, который должен оставаться
честным. Этот обход — один сеанс в git-репозитории, который у вас уже
есть, и каждый шаг — то, что вы завтра сделаете снова.

## 1. Сделайте NMOX Studio редактором git

**Сделайте:** Команда ▸ **Использовать NMOX Studio с Git…**

**Увидите:** шесть глобальных настроек git, которые делают NMOX Studio
редактором, difftool и mergetool для git, каждая рядом со значением,
которое у неё **сейчас**, так что ничего не заменяется незаметно.
**Применить** устанавливает их (**Закрыть** — кнопка по умолчанию, потому
что это записывает вашу глобальную конфигурацию git); **Копировать
команды** вместо этого кладёт строки `git config` в буфер обмена. Если git
уже использует NMOX Studio, диалог так и говорит и не предлагает
«Применить».

Те же строки, если вы предпочитаете терминал:

```bash
git config --global core.editor "nmox -w"
git config --global diff.tool nmox
git config --global difftool.nmox.cmd 'nmox -w -d "$LOCAL" "$REMOTE"'
git config --global merge.tool nmox
git config --global mergetool.nmox.cmd 'nmox -w "$MERGED"'
git config --global mergetool.nmox.trustExitCode false
```

## 2. Зафиксируйте

**Сделайте:** измените файл, затем в терминале:

```bash
git commit -a
```

**Увидите:** сообщение коммита открывается в NMOX Studio, а строка
состояния говорит, что его ждёт терминал. Строки git с `#` — это
комментарии; орфография проверяется только в том, что пишете вы; строка
сводки длиннее 72 символов, на которых её обрезают собственные
инструменты git, получает предупреждение после 72-го. Сохраните, закройте
вкладку — и коммит сделан: терминал ждал, пока вы это сделаете. Если
выйти из IDE, пока сообщение ещё открыто, оно тоже возвращается к git — с
тем, что было сохранено.

`git rebase -i` открывает свой список так же: каждая команда и каждый
коммит подсвечены, а **Закомментировать/раскомментировать** убирает
строку, не удаляя её.

## 3. Знайте, где вы находитесь

**Увидите:** **значок ⎇** в строке состояния — `⎇ main ±3 ↑2 ↓1` — это
ваша ветка, три изменённых файла, два коммита, которые нужно отправить, и
один, который нужно получить (стрелки появляются, только когда есть что
отправить или получить). Его меню начинается с **Переключить ветку…**, **Зафиксировать…**, **Получить (pull)…** и
**Отправить (push)…**.

**Сделайте:** поставьте курсор на любую строку файла под версионным
контролем.

**Увидите:** рядом со значком — кто последним изменил эту строку, как
давно и зачем: `Ada Lovelace, 3 дня назад · Fix the parser`. Строка,
которую вы ещё не зафиксировали, так и говорит, а файл с несохранёнными
изменениями говорит об этом, вместо того чтобы назвать не того автора.
Щёлкните по заметке, чтобы увидеть аннотации всего файла, коммит на GitHub
или его идентификатор; **Вид ▸ Автор строки** её отключает.

## 4. Просмотрите диф

**Сделайте:**

```bash
git difftool
```

**Увидите:** каждый изменённый файл бок о бок в представлении различий
NMOX Studio, с **Предыдущее различие / Следующее различие** и «Различие 2
из 5» над ним. У добавленного или удалённого файла отсутствующая сторона
показана пустой панелью («нет файла»); двоичный файл показан как двоичный,
а полоса говорит, различаются ли два двоичных файла. Закройте вкладку — и
git перейдёт к следующему файлу.

## 5. Разрешите конфликт

**Сделайте:** слейте ветку, которая конфликтует, затем:

```bash
git mergetool
```

**Увидите:** файл с конфликтом в редакторе, текущая и входящая стороны
подкрашены, и предупреждение на каждой строке `<<<<<<<`. Поставьте на неё
курсор и нажмите ⌘. (в других системах Alt+Enter) или выберите
**Исходный код ▸ Исправить код…**: **Принять текущее изменение**,
**Принять входящее изменение** или **Принять оба изменения** — каждое
одна отменяемая правка. Блок, изменившийся с момента предложения,
отклоняется, а не угадывается. Сохраните, закройте вкладку и ответьте git.

## 6. Предложите изменения

**Сделайте:** выполните push, затем Команда ▸ **Новый pull request на
GitHub** (он есть и в меню значка).

**Увидите:** собственную страницу GitHub New Pull Request для вашей ветки
в вашем браузере, где вы уже вошли. Из редактора **Правка ▸ Открыть на
GitHub** и **Копировать ссылку GitHub** дают строку или строки, на которых
вы стоите; в дереве Студии проекта они дают файл или папку.

## 7. Найдите причину сбоя

**Сделайте:** запускайте тесты в Терминале (⌃\`), пока один не упадёт.

**Увидите:** место в выводе — `src/app.ts:42:7`, кадр стека
`(/abs/app.js:10:5)`, `--> src/main.rs:3:5`, `File "x.py", line 12` —
открывается на этой строке и в этом столбце по ⌘-щелчку (Ctrl-щелчок в
Windows и Linux). URL или `localhost:3000` никогда не бывает ссылкой, а
путь, которого нет, отклоняется с указанием имени, а не угадывается.

## 8. Держите README честным

**Сделайте:** Сервис ▸ **Проверить ссылки Markdown…**

**Увидите:** каждая относительная ссылка и каждое изображение в Markdown
проекта проверены так, как их отображает GitHub: файл должен существовать,
а `#heading` должен быть заголовком этого файла. Мёртвая ссылка — ошибка,
отсутствующий заголовок — предупреждение, и то и другое волнистым
подчёркиванием и в окне «Задачи», с одной фразой в строке состояния.
Ничто не покидает ваш компьютер: ссылка со схемой не проверяется.

## 9. Передайте агенту

**Сделайте:** Сервис ▸ **Agent Port (MCP)…**, отметьте **Сохранить этот
адрес и токен**, затем **Копировать для Claude Code** и один раз
выполните скопированную строку.

**Увидите:** агента, который может читать то, что знает IDE, — проект, на
который она нацелена, что обслуживается и что запущено, что вы
редактируете, последний сбой — и который подключится и завтра, потому что
токен хранится в связке ключей вашей системы, а порт используется снова.
Порт остаётся только для чтения по построению. Снятие отметки **Сохранить
этот адрес и токен** удаляет запись из связки ключей.

## Что вы сделали

Вы написали сообщение коммита, прочитали диф, разрешили конфликт, открыли
pull request, узнали, кто написал строку, прошли по трассировке стека и
проверили README — всё в том окне, где вы уже были. Ничто из этого не
заменило git: каждый шаг — собственный шаг git, открытый там, где вы
работаете.
