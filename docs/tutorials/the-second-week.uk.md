*Фіксувати, переглядати, розв’язувати, пропонувати — не переходячи до іншого інструмента.*

Перша година — це відкрити проєкт і запустити його. Другий тиждень — усе,
що навколо коду: двадцять комітів на день, диф, який треба прочитати перед
кожним, конфлікт після pull, pull request після push, трасування стека, за
яким треба пройти, README, який має лишатися чесним. Цей обхід — один
сеанс у git-репозиторії, який у вас уже є, і кожен крок — те, що ви завтра
зробите знову.

## 1. Зробіть NMOX Studio редактором git

**Зробіть:** Команда ▸ **Використовувати NMOX Studio з Git…**

**Побачите:** шість глобальних налаштувань git, які роблять NMOX Studio
редактором, difftool і mergetool для git, кожне поруч зі значенням, яке
воно має **зараз**, тож ніщо не замінюється непомітно. **Застосувати**
встановлює їх (**Закрити** — кнопка за замовчуванням, бо це записує вашу
глобальну конфігурацію git); **Копіювати команди** натомість кладе рядки
`git config` у буфер обміну. Якщо git уже використовує NMOX Studio, діалог
так і каже й не пропонує «Застосувати».

Ті самі рядки, якщо ви віддаєте перевагу терміналу:

```bash
git config --global core.editor "nmox -w"
git config --global diff.tool nmox
git config --global difftool.nmox.cmd 'nmox -w -d "$LOCAL" "$REMOTE"'
git config --global merge.tool nmox
git config --global mergetool.nmox.cmd 'nmox -w "$MERGED"'
git config --global mergetool.nmox.trustExitCode false
```

## 2. Зафіксуйте

**Зробіть:** змініть файл, потім у терміналі:

```bash
git commit -a
```

**Побачите:** повідомлення коміту відкривається в NMOX Studio, а рядок
стану каже, що на нього чекає термінал. Рядки git із `#` — це коментарі;
правопис перевіряється лише в тому, що пишете ви; рядок підсумку, довший
за 72 символи, на яких його обрізають власні інструменти git, отримує
попередження після 72-го. Збережіть, закрийте вкладку — і коміт зроблено:
термінал чекав, доки ви це зробите. Якщо вийти з IDE, поки повідомлення
ще відкрите, воно теж повертається до git — з тим, що було збережено.

`git rebase -i` відкриває свій список так само: кожна команда й кожен
коміт підсвічені, а **Перемкнути коментар** прибирає рядок, не видаляючи
його.

## 3. Знайте, де ви є

**Побачите:** **значок ⎇** у рядку стану — `⎇ main ±3 ↑2 ↓1` — це ваша
гілка, три змінені файли, два коміти, які треба надіслати, і один, який
треба отримати (стрілки з’являються, лише коли є що надіслати чи
отримати). Його меню починається з **Перемкнути гілку…**, **Зафіксувати…**, **Отримати (pull)…** і
**Надіслати (push)…**.

**Зробіть:** поставте курсор на будь-який рядок файлу під версійним
контролем.

**Побачите:** поруч зі значком — хто останнім змінив цей рядок, як давно
і навіщо: `Ada Lovelace, 3 дні тому · Fix the parser`. Рядок, який ви ще
не зафіксували, так і каже, а файл із незбереженими змінами каже про це,
замість того щоб назвати не того автора. Клацніть нотатку, щоб побачити
анотації всього файлу, коміт на GitHub або його ідентифікатор; **Вигляд ▸
Автор рядка** її вимикає.

## 4. Перегляньте диф

**Зробіть:**

```bash
git difftool
```

**Побачите:** кожен змінений файл поруч в поданні відмінностей NMOX
Studio, з **Попередня відмінність / Наступна відмінність** і «Відмінність
2 з 5» над ним. У доданого чи видаленого файлу відсутня сторона показана
порожньою панеллю («немає файлу»); двійковий файл показано як двійковий, а
смуга каже, чи відрізняються два двійкові файли. Закрийте вкладку — і git
перейде до наступного файлу.

## 5. Розв’яжіть конфлікт

**Зробіть:** злийте гілку, що конфліктує, потім:

```bash
git mergetool
```

**Побачите:** файл із конфліктом у редакторі, поточна й вхідна сторони
підфарбовані, і попередження на кожному рядку `<<<<<<<`. Поставте на нього
курсор і натисніть ⌘. (в інших системах Alt+Enter) або виберіть
**Вихідний код ▸ Виправити код…**: **Прийняти поточну зміну**, **Прийняти
вхідну зміну** або **Прийняти обидві зміни** — кожна одна скасовувана
правка. Блок, що змінився відтоді, як його запропоновано, відхиляється, а
не вгадується. Збережіть, закрийте вкладку й відповідайте git.

## 6. Запропонуйте зміни

**Зробіть:** виконайте push, потім Команда ▸ **Новий pull request на
GitHub** (він є і в меню значка).

**Побачите:** власну сторінку GitHub New Pull Request для вашої гілки у
вашому браузері, де ви вже ввійшли. З редактора **Редагування ▸ Відкрити
на GitHub** і **Копіювати посилання GitHub** дають рядок або рядки, на
яких ви стоїте; у дереві Студії проєкту вони дають файл або теку.

## 7. Знайдіть причину збою

**Зробіть:** запускайте тести в Терміналі (⌃\`), доки один не впаде.

**Побачите:** місце у виводі — `src/app.ts:42:7`, кадр стека
`(/abs/app.js:10:5)`, `--> src/main.rs:3:5`, `File "x.py", line 12` —
відкривається на цьому рядку й у цьому стовпці за ⌘-клацанням
(Ctrl-клацання у Windows і Linux). URL або `localhost:3000` ніколи не є
посиланням, а шлях, якого немає, відхиляється з назвою, а не вгадується.

## 8. Тримайте README чесним

**Зробіть:** Інструменти ▸ **Перевірити посилання Markdown…**

**Побачите:** кожне відносне посилання й кожне зображення в Markdown
проєкту перевірені так, як їх показує GitHub: файл має існувати, а
`#heading` має бути заголовком цього файлу. Мертве посилання — помилка,
відсутній заголовок — попередження, і те, й інше хвилястим підкресленням
і у вікні «Завдання», з одним реченням у рядку стану. Ніщо не залишає
вашого комп’ютера: посилання зі схемою не перевіряється.

## 9. Передайте агентові

**Зробіть:** Інструменти ▸ **Agent Port (MCP)…**, позначте **Зберігати
цю адресу й токен**, потім **Копіювати для Claude Code** і один раз
виконайте скопійований рядок.

**Побачите:** агента, який може читати те, що знає IDE, — проєкт, на який
вона націлена, що обслуговується й що запущено, що ви редагуєте, останній
збій — і який під’єднається й завтра, бо токен зберігається у сховищі
ключів вашої системи, а порт використовується знову. Порт лишається лише
для читання за побудовою. Зняття позначки **Зберігати цю адресу й токен**
видаляє запис зі сховища ключів.

## Що ви зробили

Ви написали повідомлення коміту, прочитали диф, розв’язали конфлікт,
відкрили pull request, з’ясували, хто написав рядок, пройшли за
трасуванням стека й перевірили README — усе в тому вікні, де ви вже були.
Ніщо з цього не замінило git: кожен крок — власний крок git, відкритий
там, де ви працюєте.
