Ваші руки вже знають, де що лежить. Ця сторінка — мапа від цих звичок до NMOX Studio: спершу сполучення клавіш, потім де живе кожна ідея VS Code, а наостанок — що тут чесно інакше.

Перші чотири сполучення, які натискає користувач VS Code, роблять те, чого він чекає: **⇧⌘P** відкриває палітру команд, **⇧⌘E** — дерево файлів, **⇧⌘X** — плагіни, а **⌃\`** — термінал. Їх записано в усіх п’ятьох профілях розкладки, які постачає платформа, а затвор збирання перевіряє кожне з них у зібраній розкладці на macOS, Windows і Linux, щоб замість нього не спрацювало щось інше.

<a id="the-chords"></a>
## Сполучення клавіш

Стовпці macOS використовують значки з рядка меню (⌃ Control, ⌥ Option, ⇧ Shift, ⌘ Command); стовпці Windows і Linux — це те саме сполучення на клавіатурі ПК.

| Що потрібно | VS Code, macOS | NMOX, macOS | VS Code, Win/Linux | NMOX, Win/Linux |
|---|---|---|---|---|
| Палітра команд | ⇧⌘P | **⇧⌘P** (або ⌘I) — Швидкий пошук | Ctrl+Shift+P | **Ctrl+Shift+P** (або Ctrl+I) |
| Відкрити файл за назвою | ⌘P | **⌘P** — Перейти до файлу | Ctrl+P | **Ctrl+P** |

| Розширення | ⇧⌘X | **⇧⌘X** — Інструменти ▸ Плагіни | Ctrl+Shift+X | **Ctrl+Shift+X** |
| Термінал у теці проєкту | ⌃\` | **⌃\`** | Ctrl+\` | **Ctrl+\`** |
| Відкрити недавній проєкт | ⌃R | **⌥⌘P** — Змінити проєкт… | Ctrl+R | **Ctrl+Alt+P** |

| Перейти до рядка | ⌃G | **⌃G** | Ctrl+G | **Ctrl+G** |
| Назад / вперед | ⌃- / ⌃⇧- | **⌃- / ⌃⇧-** | Alt+← / Alt+→ | **Alt+← / Alt+→** |

| Виділити всі входження | ⇧⌘L | **⌃⇧⌘J** | Ctrl+Shift+L | **Ctrl+Alt+Shift+J** |
| Додати курсор вище / нижче | ⌥⌘↑ / ⌥⌘↓ | **⌥⌘↑ / ⌥⌘↓** | Ctrl+Alt+↑ / ↓ | **Alt+Shift+[ / ]** |

| Скопіювати його відносний шлях | ⇧⌥⌘C | Редагування ▸ Копіювати відносний шлях (без сполучення) | Ctrl+K Ctrl+Shift+Alt+C | Редагування ▸ Копіювати відносний шлях (без сполучення) |

На macOS ⌘, належить самому меню застосунку; кожне інше сполучення NMOX у таблиці прочитано з поставленої розкладки, а не згадано з пам’яті. Кілька речей, які не вмістити в клітинку:

- **F5 зайнята під час зневадження.** Тут вона означає *Продовжити*, як у кожній IDE родини NetBeans, тож запуск зі зневадженням починається з **⇧⌘F5** (Ctrl+Shift+F5), а продовжується з F5.
- **⌃R тут — перейменування**, тому *Змінити проєкт* живе на ⌥⌘P, а не на сполученні Open Recent із VS Code. Перейменування працює там, де його підтримує мова, що стоїть за файлом.
- **«Копіювати відносний шлях» не має сполучення.** ⇧⌥⌘C із VS Code на PC — це Ctrl+Alt+Shift+C, а це *Clear Split* платформи в кожному профілі клавіатури; рядок є в меню «Редагування», і ⇧⌘P знаходить його за власною назвою VS Code, *File: Copy Relative Path of Active File*.
- **Ctrl+, у Windows і Linux** веде назад історією ваших правок, як це завжди було в NetBeans; налаштування — у меню Інструменти ▸ Налаштування (на macOS — **Settings…** у меню застосунку, ⌘,).

**Довідка ▸ Клавіатурні скорочення…** перелічує кожне сполучення NMOX у вашій чинній розкладці, разом із чотирма сполученнями VS Code, прочитане з розкладки, що працює, тож воно не може розійтися з тим, що роблять клавіші.

### Кожне сполучення для редагування, виміряне

Сполучення, до яких тягнуться ваші руки з VS Code під час редагування, кожне знайдене в розкладці, що постачається, для типового профілю на macOS. Де сполучення VS Code тут було вільне, тепер воно робить те саме, що у VS Code (рядки з позначкою **Те саме:**); де воно вже означало щось, на що покладаються користувачі NetBeans, воно зберігає це значення, а рядок каже, де знаходиться дія VS Code.

| VS Code, macOS | Що робить VS Code | У NMOX Studio |
|---|---|---|
| F12 | Go to Definition | **Те саме:** Перейти до оголошення, як ⌘B |
| ⇧F12 | Go to References | **Те саме:** Знайти використання, як ⌃F7 |
| F2 | Rename Symbol | **Те саме:** Перейменувати, як ⌃R |
| ⌘. | Quick Fix | **Те саме:** виправлення для рядка, які показує ⌃↩ |
| ⌥↑ / ⌥↓ | Move Line Up / Down | Попереднє / наступне позначене входження; рядок переміщують ⌃⇧↑ / ⌃⇧↓ |
| ⇧⌥↑ / ⇧⌥↓ | Copy Line Up / Down | Те саме, як було завжди |
| ⇧⌘K | Delete Line | Вставити наступне збіжне слово (доповнює слово з файлу); рядок видаляє ⌘E |
| ⌘L | Expand Line Selection | Виділити ідентифікатор — у типовій розкладці сполучення лишається за ним; «Розширити виділення на рядок» є у Швидкому пошуку під цією назвою, а в профілях розкладки IntelliJ та Emacs, які лишають це сполучення вільним, — на самому ⌘L |
| ⇧⌘L | Select All Occurrences | Вставити як рядки в редакторі; усі входження виділяє ⌃⇧⌘J |
| ⌘/ | Toggle Line Comment | Те саме, як було завжди |
| ⇧⌥A | Toggle Block Comment | **Те саме:** бере виділення або рядок із курсором у блокові роздільники мови й знімає їх знову; виділення, у якому вже є роздільник, відхиляється, а не ламається |
| ⌘] | Indent Line | **Те саме:** Зсунути праворуч |
| ⌘[ | Outdent Line | Перехід до парної дужки, як було завжди; відступ прибирають ⇧Tab або ⌃⇧← |
| ⌥Z | Toggle Word Wrap | **Те саме:** Вигляд ▸ Перенесення рядків. Перемикає перенесення для кожного редактора мови цього файлу, а не для однієї вкладки, і вибір зберігається |
| ⌘B | Toggle Sidebar | Перейти до оголошення; ⇧⌘↩ лишає тільки редактор, ⇧Esc розгортає вікно, у якому ви перебуваєте |
| ⌘J | Toggle Panel | Додає наступне входження в редакторі (як ⌘D); вікно **Output** — ⌘4 |
| ⌘\ | Split Editor | Доповнити код у редакторі; редактор розділяє ⌃⇧⌘V |
| ⇧⌘T | Reopen Closed Editor | Те саме, як було завжди: сполучення «Відкрити недавній файл» знову відкриває останній закритий файл |
| ⌃- / ⌃⇧- | Go Back / Go Forward | **Те саме:** Назад і Вперед місцями, де ви редагували, як ⌃← / ⌃→ (сполучення, які macOS зазвичай лишає для перемикання робочих столів) |
| ⌘G / ⇧⌘G | Find Next / Previous | Те саме, як було завжди |
| ⌥⌘F | Replace | **Те саме:** Замінити, як ⌘R |
| ⇧⌘F | Find in Files | Те саме, як було завжди: Знайти у проєктах |
| ⇧⌘O | Go to Symbol in Editor | Відкрити проєкт; символи файлу — у Швидкому пошуку: ⌘I, потім `@name`, як у VS Code (Перехід ▸ Перейти до символу в цьому файлі… вводить `@` за вас), і деревом у Навігаторі (⌘7) |
| ⌘T | Go to Symbol in Workspace | Міняє місцями дві літери біля курсора в редакторі; символи проєкту — ⌥⇧⌘O |
| ⌃G | Go to Line | Те саме, як було завжди |
| ⌘K ⌘S | Keyboard Shortcuts | ⌘K — Вставити попереднє збіжне слово; список — **Довідка ▸ Клавіатурні скорочення…** |
| ⌘, | Settings | Те саме, як було завжди: NMOX Studio ▸ Settings… |
| ⇧⌥F | Format Document | **Те саме:** Форматувати, як ⌃⇧F |

Сполучення з позначкою **Те саме:** призначені в кожному профілі розкладки, який лишає їх вільними, а профіль, що дає одному з них власне значення, це значення зберігає: F12 у профілях Eclipse, Emacs і NetBeans 5.5, F2 у всіх профілях, крім типового, ⇧F12 в Emacs і NetBeans 5.5, ⌃- і ⌃⇧- в Emacs і IntelliJ, ⇧⌥F в IntelliJ. У Windows і Linux F12, ⇧F12 і F2 працюють так само; решта сполучень VS Code там інші, і таблиця вище наводить обидва варіанти.

«Перемкнути блоковий коментар» і «Перемкнути перенесення рядків» мають свої сполучення з VS Code також у Windows і Linux. Перенесення рядків — це Alt+Z у кожному профілі. Блоковий коментар — це Shift+Alt+A в типовому профілі та в профілях Emacs й IntelliJ (профілі Eclipse і NetBeans 5.5 зберігають там власне значення Alt+Shift+A), а в Linux це ще й Ctrl+Shift+A, сполучення VS Code для Linux, в усіх п’ятьох. «Розширити виділення на рядок» у Windows і Linux — це Ctrl+L лише в профілі IntelliJ; у профілі Emacs Ctrl+L там і далі означає власне *recenter* самого Emacs.

Мова без блокового коментаря, як-от Python, каже про це в рядку стану. У файлі HTML, Vue чи Svelte блок `<script>` або `<style>` коментується як його власна мова, як і frontmatter компонента Astro; виділення, яке занесло б коментар у такий блок або винесло б його звідти, відхиляється з назвою, а не ламає файл. Без виділення сполучення ставить і знімає коментар на рядку; воно не шукає коментар, який просто оточує курсор, тож щоб прибрати коментар на кілька рядків, виділіть його.

У Швидкому пошуку символи файлу — це категорія **Символи в цьому файлі**. Якщо ввести лише `@`, вони перелічуються від початку файлу; `m name` (літера, пробіл, потім назва) шукає в цій категорії й у жодній іншій.

### Профіль розкладки VS Code

Таблиці вище описують типовий профіль, де сполучення, на яке покладаються користувачі NetBeans, зберігає своє значення. Якщо ваші руки хочуть розкладку VS Code цілком, перемкніть профіль: наберіть *Використовувати розкладку клавіш VS Code* у Швидкому пошуку (⇧⌘P або ⌘I; рядок називається *Preferences: Use the VS Code Keymap*) або виберіть **VS Code** в Інструменти ▸ Налаштування ▸ Комбінації клавіш ▸ Profile (на macOS — NMOX Studio ▸ Settings… ▸ Комбінації клавіш ▸ Profile). Рядок стану каже, у якому профілі ви перебуваєте і як повернутися; ніщо ніколи не перемикає його за вас.

У цьому профілі типові сполучення VS Code роблять те саме, що й у VS Code, — на macOS так само, як у Windows і Linux, — скрізь, де цей продукт має відповідну дію: ⌥↑ / ⌥↓ переміщують рядок, ⇧⌘K видаляє його, ⌘L розширює виділення на рядок, ⇧⌘L виділяє всі входження, ⌘[ / ⌘] зсувають ліворуч і праворуч, ⌘↩ вставляє рядок нижче, ⇧⌘\\ переходить до парної дужки, ⌥⌘[ / ⌥⌘] згортають і розгортають, ⌘K ⌘0 / ⌘K ⌘J згортають і розгортають усе, ⌘K ⌘X прибирає кінцеві пробіли, ⌘J показує вікно Output, ⌘\\ розділяє редактор, ⌘T і ⇧⌘O переходять до символу в проєкті та у файлі, ⇧⌘M показує **Завдання**, ⇧⌘D — вікно зневаджувача, ⌘K ⌘S — аркуш «Клавіатурні скорочення», ⌘K ⌘W закриває всі редактори, ⌘K ⌘O відкриває теку, ⌃R відкриває нещодавній проєкт, ⇧⌘B збирає, F1 — палітра команд, а клавіші зневаджувача — ті, що у VS Code: F5 починає зневадження проєкту або продовжує призупинене, ⇧F5 зупиняє, ⌃F5 запускає без зневадження, F9 ставить чи знімає точку зупину, F10, F11 і ⇧F11 — крок через, усередину та назовні. Кожне сполучення продукту, якого VS Code не забирає собі (вікна на ⌥⌘, ⌥⌘E від Emmet, ⌥⌘G), лишається там, де було.

Що все ще інакше в профілі VS Code, поіменно:

- **Жодного сполучення**, бо такої дії тут немає: ⌘B (*Toggle Primary Side Bar*), ⇧⌘W (*Close Window*), ⇧⌘F5 (*Restart* зневадження), F8 / ⇧F8 (*Go to Next / Previous Problem in Files*), ⌥F12 (*Peek Definition*), ⇧⌘↩ (*Insert Line Above*) і ⌘U (*Cursor Undo*). Ці клавіші не роблять нічого, а не щось інше.
- **«Зберегти все» не має сполучення у Windows і Linux** (у VS Code це Ctrl+K S); на macOS це ⌥⌘S.
- **Що сполучення VS Code забрали в NetBeans.** F1 більше не відкриває довідку, ⌘B більше не переходить до оголошення (це робить F12), а перетворення регістру на ⌘U, доповнення слова на ⌘K / ⇧⌘K, перестановка на ⌘T та історія буфера обміну на ⇧⌘D у цьому профілі не мають сполучення, як і «Налагодити файл», «Перемкнути закладку», «Показувати лише редактор» і «Відкрити проєкт». Повний список для кожної ОС — `scripts/vscode-keymap/displaced.txt` у вихідному коді.

## З термінала

`code .` — це `nmox .`:

```bash
cd ~/code/my-app
nmox .          # open this folder (manifest or not) and aim the IDE at it
nmox src/app.ts # open one file
nmox src/app.ts:42  # open it at line 42 (code -g's form; -g itself is accepted)
nmox            # just start the IDE
```

Команда повертається одразу, а другий `nmox` передає свою теку IDE, що вже працює. Стовпець (`src/app.ts:42:7`) теж приймається, і редактор відкривається на початку рядка; ім’я, якого немає, відхиляється просто в терміналі, і нічого не запускається. Ключ `-r` приймається, `-n` відкриває в тому самому єдиному вікні, а `-a` та `-v` відхиляються за назвою.

`-w` (`--wait`) відкриває файл і чекає, доки ви не закриєте його вкладку, а `-d` (`--diff`) порівнює два файли поруч, тож NMOX Studio може бути редактором, difftool і mergetool для git, як `code --wait`:

```bash
git config --global core.editor "nmox -w"
git config --global diff.tool nmox
git config --global difftool.nmox.cmd 'nmox -w -d "$LOCAL" "$REMOTE"'
git config --global merge.tool nmox
git config --global mergetool.nmox.cmd 'nmox -w "$MERGED"'
git config --global mergetool.nmox.trustExitCode false
```

Тоді `git commit` відкриває повідомлення в IDE; збережіть його і закрийте вкладку, і git продовжить. Вихід з IDE, поки файл ще відкритий, теж повертає його — з тим, що було збережено. `git mergetool` відкриває кожен файл із конфліктом так само. Там, де VS Code ставить над конфліктом *Accept Current Change | Accept Incoming Change | Accept Both Changes*, NMOX Studio підфарбовує обидва боки й ставить попередження на рядок `<<<<<<<`; лампочка на полях або швидке виправлення з курсором на цьому рядку (⌘. на Mac, Alt+Enter в інших системах) пропонують ті самі три варіанти, кожен — одна правка, яку можна скасувати. Збережіть, закрийте вкладку, і git перейде до наступного файлу. Підсвічування й три варіанти є в будь-якому файлі з маркерами конфлікту, з `git mergetool` чи без нього. **Команда ▸ Використовувати NMOX Studio з Git…** виставляє ті самі рядки за вас, спершу показавши, яке значення має кожен із них зараз. Homebrew, інсталятор Windows (*Add "nmox" to PATH*, «Додати nmox до PATH») і пакети Linux кладуть її у PATH; для встановлення з DMG [посібник користувача](user-guide.uk.md#2-first-launch) показує посилання в один рядок.

<a id="what-is-honestly-different"></a>
## Що тут чесно інакше

- **У типовому профілі ⌘D додає наступне входження, але не в кожному профілі.** Профіль Eclipse залишає ⌘D за *Delete Line* середовища Eclipse, профіль NetBeans 5.5 — за *Shift Line Left*, а профіль Emacs — за *kill word* (і Ctrl+D — за *delete character* у Windows і Linux); у профілі IntelliJ ⌘D працює на macOS, а Ctrl+D у Windows і Linux лишається за *Duplicate Line*. Друге сполучення для цього жесту теж залежить від профілю: ⌘J (Ctrl+J) у типовому, ⌃J (Alt+J) в Eclipse та IntelliJ і жодного в Emacs і NetBeans 5.5, де його можна призначити в «Комбінаціях клавіш».
- **⌃\` відкриває Термінал і переводить на нього фокус, але не ховає його.** А поки фокус у Терміналі, клавіші належать вашій оболонці, тож друге натискання дістається оболонці, а не повертає вас у редактор.
- **`launch.json` читається, а те, чого зневаджувач не може виконати, відхиляється.** Зневаджувач тут передає програму, її робочу теку, її `args` (список рядків), її `env` та `envFile` і середовище виконання, яке її запускає (`runtimeExecutable` і `runtimeArgs` для Node, `python` для Python); для Node він ще й приєднується до процесу, що вже працює. Конфігурація, що задає `postDebugTask`, `restart` чи будь-яке інше поле, якого його не навчили, є в списку, але не запускається: Ввід називає ці поля в рядку стану. Запустити програму без них означало б зневаджувати не те, що написано у файлі. Так само відхиляються `args` або `runtimeArgs`, записані одним рядком (такий рядок VS Code віддає оболонці), і значення `null` в `env` (воно видаляє змінну), а також запис `compounds`, тип, для якого тут немає адаптера (`go`, `msedge`, `cppdbg` та інші), приєднання до будь-чого, крім Node, значення, яке може підставити лише VS Code (`${input:…}`, `${command:…}`), і програма, робоча тека чи `envFile` за межами проєкту. Поля, що лише змінюють те, що показує зневаджувач, — `skipFiles`, `outFiles`, `sourceMaps`, `console`, `justMyCode`, `presentation`, — приймаються, але не застосовуються; вивід програми йде у вікно Output. П’ять речей варто знати, перш ніж натиснути Ввід:
  - **`preLaunchTask` виконується першим і мусить завершитися успішно.** Завдання виконується так, як його запустив би Ввід на ньому у Швидкому пошуку, — завдання з його `dependsOn`, його запитання, його власна вкладка Output, — а зневаджувач запускається, коли воно завершилося з кодом виходу 0; там, де VS Code після невдалого завдання питає *Debug Anyway?*, тут рядок стану каже, що конфігурацію не запущено. `program`, який збирає це завдання (`dist/server.js`), шукають після завдання, а не до нього. Мітка, якої `tasks.json` не визначає, мітка, спільна для двох завдань, і форма об’єкта (`{"type": "npm", "script": "build"}`) відхиляються за назвою, перш ніж щось запуститься. На фонове завдання (`"isBackground": true`, спостерігач, який ніколи не завершується) чекають, доки його зіставник проблем не повідомить про завершений цикл, після чого воно працює далі, а наступне зневадження використовує його знову; фонове завдання без зіставника, який міг би сказати, коли воно готове, відхиляється за назвою.
  - **`envFile`, якого немає, відхиляється**, тоді як VS Code запускає програму без нього. Його змінні додаються до оточення, а запис в `env` перемагає файл, як і у VS Code. Файл читається як прості рядки `NAME=value` (рядки-коментарі, `export` і одна пара лапок довкола значення — це нормально); рядок, який VS Code прочитав би інакше, — екранування всередині подвійних лапок, `#` після значення, зворотний апостроф, а в конфігурації Python ще й `export` чи `${NAME}`, — відхиляється з назвою файлу й номером рядка, але ніколи не зі значенням.
  - **`${file}`, `${relativeFile}`, `${fileBasename}`, `${fileBasenameNoExtension}`, `${fileExtname}`, `${fileDirname}` та інші файлові змінні означають файл активного редактора**: вкладку з фокусом, якщо це редактор, а інакше — вкладку, показану в ділянці редактора; це той самий файл, який означає `${file}` у завданні. Коли жодного файлу не відкрито, конфігурація відхиляється з назвою змінної, а `${file}` за межами проєкту відхиляється, як і будь-яка інша програма там.
  - **`runtimeExecutable` — це назва або абсолютний шлях.** Назву (`npm`, `tsx`, `nodemon`) шукають у вашому PATH, а потім у `node_modules/.bin` проєкту; `${workspaceFolder}/node_modules/.bin/tsx` мусить там бути; відносний шлях відхиляється, бо VS Code шукав би його як назву. Коли середовище виконання — це вся команда (`npm run dev` без `program`), скрипт, який воно запускає, зневаджується як окремий сеанс, показаний у вікні Sessions.
  - **Приєднання — лише до цієї машини.** `port` (9229, якщо не написано інше) та `address` зі значенням `localhost`, `127.0.0.1` або `::1`; будь-яка інша адреса відхиляється, бо це не віддалена розробка. Якщо ніщо не слухає, про це каже рядок стану, а завершення сеансу лишає вашу програму працювати.
- **`tasks.json` читається, а те, що не можна виконати так, як написано, відхиляється.** Завдання виконується після завдань, названих у його `dependsOn` (разом або одне за одним із `"dependsOrder": "sequence"`), зі змінними `${file}`, `${relativeFile}`, `${lineNumber}`, `${selectedText}` та рештою цієї родини, заповненими з файлу, відкритого в редакторі, а його запитання `${input:…}` (`promptString`, `pickString`) ставляться, перш ніж щось запуститься. Спершу вирішується весь запуск: якщо хоч одне його завдання не можна виконати так, як написано, не виконується нічого, а Ввід каже в рядку стану, яке завдання і чому. Це стосується мітки в `dependsOn`, якої файл не визначає, залежності, яка є фоновим завданням без зіставника проблем, що міг би сказати, коли воно готове, `${file}`, коли жодного файлу не відкрито, і запитання, яке ви скасували. Залежність, що завершилася невдало, зупиняє запуск на цьому місці. Як і раніше, відхиляються за назвою: значення, яке може підставити лише VS Code (`${config:…}`, `${command:…}`, вхідне значення з `"type": "command"`), залежність, записана об’єктом (`{"type": "npm", …}`), а не міткою, тип завдання, який дає розширення (`gulp`, `typescript`), і робоча тека за межами проєкту.
- **Фрагменти — це фрагменти вашого репозиторію, і три речі відрізняються.** Вибір (`${1|a,b|}`) починається зі свого першого варіанта, без списку, з якого можна вибирати; заповнювач, вкладений у типове значення іншого, стає частиною цього типового значення; а фрагмент, перетворення якого не можна виконати безпечно (регулярний вираз, який Java не може скомпілювати, або такий, що міг би працювати без кінця), пропускається й називається в журналі, а не вставляється наполовину. Набирання префікса саме не відкриває список: це робить ⌃Space. Фрагменти без `prefix`, фрагменти рівня користувача та `isFileTemplate` не читаються. Файли фрагментів читаються лише для файлів усередині репозиторію, який їх містить, а фрагмент, що вставив би понад мільйон символів, не вставляється.
- **`problemMatcher` завдання читається.** Кожен запуск замінює попередні проблеми цього завдання, а чистий запуск їх очищає. Вбудовані зіставники VS Code працюють за назвою (`$tsc`, `$tsc-watch`, `$tsgo-watch`, `$eslint-stylish`, `$eslint-compact`, `$jshint`, `$jshint-stylish`, `$msCompile`, `$lessCompile`, `$gulp-tsc`, `$go`, `$lessc`), як і `$gcc` та `$rustc` з розширень C/C++ і rust-analyzer; працюють і зіставники, записані прямо в завданні, і `{"base": "$tsc", …}`, разом із багаторядковими шаблонами з `loop`, з будь-яким `fileLocation`, крім `"search"`. Зіставник, якого ця IDE не має або чий регулярний вираз тут означає щось інше, не зупиняє завдання: воно виконується, а рядок стану один раз називає зіставник, який не застосовано.
- **Форматування форматує JavaScript і TypeScript за допомогою Prettier проєкту.** Вихідний код ▸ Форматувати (⇧⌥F) запускає Prettier, який налаштовує ваш проєкт, і спершу питає про довіру до робочої області, коли цей Prettier — власний Prettier проєкту; проєкт без конфігурації Prettier каже про це в рядку стану, а не лишає файл таким, як був, без жодного слова.
- **Ваші власні налаштування переносяться один раз, коли ви попросите.** **Інструменти ▸ Імпортувати налаштування VS Code…** (або *import vs code settings* у Швидкому пошуку) читає ваш особистий `settings.json` VS Code — із VS Code, Insiders чи VSCodium — і перелічує кожне налаштування, яке розпізнає, разом із тим, чим воно стає тут: ширина табуляції й пробіли, перенесення рядків, лінійки, показ пробільних символів, обрізання пробілів під час збереження, «Форматувати під час збереження», мінікарта, липке прокручування й автозбереження. Налаштування, що тут означають рівно те саме, спершу позначені; близькі кажуть, чим відрізняються, і спершу не позначені. «Застосувати» записує позначені, і вони діють одразу; «Скасувати» не записує нічого. Шрифт редактора задають у налаштуваннях «Шрифти та кольори», а сполучення клавіш — це профілі розкладки. Усе інше у вашому файлі — токени, шляхи, налаштування розширень — лише підраховується, але ніколи не показується й не копіюється.
- **`files.associations` не читається.** Платформа визначає тип файлу один раз і зберігає його, тож відповідність із `settings.json` не можна було б шанувати точно; умовне виключення (`"when"`), лінійки після першої та їхні кольори, а також перенесення на певному стовпці теж не читаються.
- **Завдання `"type": "shell"` виконується в тій оболонці, яку взяв би VS Code.** На macOS і Linux це ваш `$SHELL` із `-c` (zsh, bash чи fish на macOS стартують як оболонка входу, `-l`, як у типових профілях VS Code); у Windows — PowerShell, `pwsh`, якщо його встановлено. `options.shell` шанується так, як це робить VS Code: укажіть `executable`, і оболонка запуститься рівно з тими `args`, що ви дали, тож bash потрібен `"args": ["-c"]`. У Windows запускаються лише PowerShell (аргументи закінчуються на `-Command`) і `cmd.exe` (аргументи закінчуються на `/c`); будь-яку іншу оболонку там відхилено за назвою, а не передано їй командний рядок, узятий у лапки навмання. Назва файлу, виділення чи відповідь на запитання в `command` завдання оболонки береться в лапки для цієї оболонки, тож `"command": "python ${file}"` працює для будь-якої назви файлу, навіть із пробілом чи `$`; у `cmd.exe` значення з `%`, `!`, подвійною лапкою чи розривом рядка відхиляється за назвою, бо ніякі лапки там їх не знешкоджують.
- **Таблиці вище описують типовий профіль розкладки.** У профілі **VS Code** (див. *Профіль розкладки VS Code* вище) власні сполучення VS Code перемагають скрізь, де цей продукт має відповідну дію. Перші чотири сполучення працюють у кожному профілі. Один навмисний виняток: у профілі **Eclipse** ⇧⌘E лишається власним *Switch to Editor* середовища Eclipse, а всередині редактора ⇧⌘P і ⇧⌘X зберігають значення Eclipse (парна дужка, верхній регістр) — хто обрав Eclipse, чекає Eclipse.
- **У Linux Ctrl+\` відкриває Термінал, а не перемикач вікон.** Перемикач — на Ctrl+Tab. На стільниці, що забирає Ctrl+Tab собі (KDE, наприклад), відкриті файли перелічує **Вікно ▸ Документи…**.
- **Сполучення Ctrl+Alt можуть зіткнутися з AltGr.** У Windows розкладки, які набирають символи через AltGr (польська, наприклад), надсилають для нього Ctrl+Alt. Якщо Ctrl+Alt+P чи Ctrl+Alt+K друкує вам символ, перенесіть *Змінити проєкт* або сполучення експериментів у Комбінаціях клавіш.
- **Розширення VS Code тут не встановлюються.** Інтелект мов дають мовні сервери, які знає NMOX (Діагностика середовища перелічує, чого бракує і як це встановити), власні граматики редактора та плагіни, зроблені для платформи NetBeans.
